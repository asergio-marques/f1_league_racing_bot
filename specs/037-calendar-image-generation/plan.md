# Implementation Plan: Calendar Image Generation

**Branch**: `037-calendar-image-generation` | **Date**: 2026-08-12 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/037-calendar-image-generation/spec.md`

## Summary

The calendar is the first image type to be given a generation utility. The 035 increment built
the engine — parse, fill, crop, rasterise, validity layers, notices, problems — and left every
image type's field catalogue deliberately empty, with each downstream check written to pass
vacuously until a catalogue is populated. This increment populates the first one.

The bulk of the work is therefore **not** new rendering machinery. It is: declaring the calendar's
catalogue, writing the data-to-`FillSpec` builder, wiring the two posting paths (season approval and
a new sync command), persisting a message id, and one schema migration. Two pieces of the existing
engine need genuine extension, both traced in [research.md](./research.md): the catalogue model
assumes a capacity fixed in code, and the calendar's capacity is declared by the league's template;
and the division-capacity guard counts seated drivers, which is the wrong collection for a calendar.

## Technical Context

**Language/Version**: Python 3.13
**Primary Dependencies**: discord.py (slash commands, attachments), lxml (SVG tree), aiosqlite
(storage), Inkscape (rasteriser, invoked as a subprocess and probed at conventional install paths)
**Storage**: SQLite via numbered migrations under `src/db/migrations/`; next free number is **040**
**Testing**: pytest, from the repo root as `pytest tests/ -q`
**Target Platform**: a single long-running Discord bot process on Windows or Linux
**Project Type**: single project — `src/` with `cogs/`, `services/`, `models/`, `utils/`, and `tests/`
**Performance Goals**: a season approval renders one graphic per division sequentially; the
rasteriser is a subprocess of order a second, so a ten-division season must stay within the
deferred-interaction window and must not block the event loop
**Constraints**: Discord permits at most 25 subcommands per group and no third nesting level;
an attachment cannot be added to a message already posted; the rasteriser may be absent from a host
**Scale/Scope**: one image type of fifteen; a division holds roughly 10–24 rounds

| XIV.6 Assets | Aspect-authored, never padded, referenced as a URI | ✅ `mystery.svg` authored to the directory's aspect |
| XIV.9 Layered validity | Three moments read one evaluation; declared depth; no silent pass | ⚠️ **Needs extension** — see Complexity Tracking |
| XIV.10 Catalogue as code constant | One entry, one shared module, same object for fill and Layer 2 | ⚠️ **Needs extension** — see Complexity Tracking |
| XIV.11 Id convention | `<collection>_<x>_<field>`, unpadded, contiguous from 1 | ✅ `RowSpec.prefix` already carries this; set to `round` |
| XIV.12 Capacity, fatal overflow | Capacity declared; overflow fatal at the earliest moment | ⚠️ **Needs extension** — see Complexity Tracking |
| XIV.14 Verified as PNG | Every check against the rasterised PNG | ✅ Tests assert on rasterised output, never a browser view |
| XIV.15 One time zone | Configured zone for every reader, abbreviation appended | ✅ Uses the existing configured zone and formats |

**Initial gate: PASS with three noted extensions.** None is a violation of a principle; each is a
place where the *existing implementation* of a principle assumed a shape the calendar does not
have. They are recorded in Complexity Tracking and resolved in research.md.

**Post-Phase-1 re-check: PASS.** The design resolves all three without adding a code path that
branches per image type: capacity becomes a property a catalogue may source from the template
rather than a constant, which every later type inherits.

**Structure Decision**: single project, matching the existing repository layout exactly. The
calendar adds two services and one migration; it introduces no new top-level directory and no new
architectural layer. The split between `image_calendar_service` (what to draw) and
`calendar_post_service` (where it goes and what replaces what) mirrors the existing separation
between `image_render_service` and the per-module posting services, and is what keeps the
delete-before-post ordering testable without a Discord connection.

## Complexity Tracking

> Three places where the delivered engine assumed a shape the calendar does not have. None is a
> deliberate violation; each is an extension the constitution's own wording anticipates but the
> 035 implementation did not yet need.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| `RowSpec.capacity` becomes derivable from the template rather than a fixed constant (XIV.10, XIV.12) | The calendar's slot count is whatever the league drew into its own template. A code constant cannot know it, yet XIV.12 still requires the capacity to be *declared and matched*. | Hard-coding a capacity was rejected: it would force every league onto one round count. Skipping the capacity check for the calendar was rejected: XIV.12 makes overflow fatal for every collection, which the author confirmed on 2026-08-12. |
| Layer 2 must derive the round count from the template before enumerating mandatory ids (XIV.9) | `all_mandatory_ids()` enumerates `round_1..round_N`; for the calendar N is a property of the file being checked, not of the catalogue. | Leaving Layer 2 skipped for the calendar was rejected — it would report the first specified image type as unchecked, which is the very state XIV.9 exists to end. |
| The division-capacity guard needs a second collection (XIV.12) | `placement_service._guard_image_capacity` counts **seated drivers** against the smallest capacity. A calendar's collection is **rounds**; a driver placement must not be refused by a calendar template, and adding a round must be. | Reusing the seated-driver guard was rejected as simply wrong: it would refuse the wrong command and miss the right one. |
